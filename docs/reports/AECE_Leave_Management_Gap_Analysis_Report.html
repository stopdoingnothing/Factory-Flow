Executive Summary

Overall Status: 15 of 16 requirements fully or substantially implemented.

The AECE Leave Management System is mature and production-ready. Core leave workflow functionality—including employee requests, multi-stage approvals, BCEA-compliant accrual calculations, and audit logging—is complete and operational. The system successfully implements the South African Basic Conditions of Employment Act (BCEA) requirements with proper handling of annual, sick, family responsibility, and statutory leave entitlements.

Key Strengths: Robust BCEA calculations, comprehensive audit trails, flexible custom leave type configuration, and multi-stage approval workflows with discretion logging.

Minor Gaps: Employee self-service profile updates (not critical), team-level manager alerts (nice-to-have), and several hardcoded policy values that should be configurable.

Recommendation: System is ready for production deployment. Address high-priority gaps in subsequent releases (Q3 2026).

⚠️ Partially Implemented Requirements (2)
REQ-001: Employee Self-Service Profile Updates
PARTIAL

🔴 Gap

Employees cannot self-update their contact details (mobile phone, email, home address) via the employee portal. Only HR administrators have update permissions.

Current Behavior: EmployeeDashboardSection.tsx shows read-only profile information. PersonnelSection.tsx (HR-only) has full edit capability.

Impact: Employees must contact HR to update contact information, creating administrative overhead. This violates the spec assumption that "employee self-service for HR profile updates beyond basic contact info" should be available.

What's Missing:

  • PUT /api/users/:id/self-update endpoint (restricted to own record)
  • Employee profile edit modal/form in EmployeeDashboardSection
  • Self-update audit trail to track who changed what
REQ-010: Team Coverage Alerts (Manager Notification)
PARTIAL

🔴 Gap

System sends notifications for individual request events (submission, approval, rejection), but does NOT send team-level coverage alerts to managers showing upcoming leave patterns.

Current Behavior: LeaveCalendarSection.tsx displays a calendar view of leaves, but no automated digest is sent to managers (e.g., "Your team has 15 days of leave scheduled next week").

Impact: Managers cannot proactively plan staffing and coverage. They must manually check the leave calendar to understand team availability.

What's Missing:

  • Scheduled notification job (weekly digest) showing team leave summary
  • Manager endpoint: GET /api/leave-requests/my-team?from=...&to=...
  • Email template for team coverage digest
  • Optional notification frequency setting (daily/weekly/monthly)
⚙️ Configuration & Clarity Gaps

The following features are implemented but rely on hardcoded or unclear configuration values:

1. Unpaid Leave Notice Period (Hardcoded)

Issue: The 7-day notice requirement is hardcoded in POST /api/leave-requests (line 1712). HR cannot adjust it without code changes.

Recommended Fix: Move to configurable setting: unpaid_leave_notice_days (default: 7). Expose in admin settings UI.

2. Annual Leave Cycle Start (Fixed to January 1)

Issue: Annual leave year resets on January 1 with no HR override option. Some organizations may use employment anniversary or April 1 as cycle start.

Current: Likely stored in settings table but not exposed in admin UI.

Recommended Fix: Add admin control in SettingsSection for annual_leave_cycle_start_month.

3. Medical Certificate Enforcement (Implicit)

Issue: System flags sick leave requests that need medical certificates (requiresMedCert, medCertFlags), but does NOT explicitly prevent approval without a document.

Current Behavior: HR can approve a flagged request even if no certificate is attached.

Recommended Fix: Add validation at HR approval stage: reject if flagged AND no document attached. Allow override with discretion reason.

4. Commissioning Parental Leave Eligibility (Unclear)

Issue: "Commissioning Parental Leave" (50 days) is defined in the spec but no special enrollment or eligibility criteria is documented or implemented.

Current: Treated identically to standard Parental Leave.

Recommended Fix: Clarify in spec whether this applies only to surrogacy arrangements. If so, add is_surrogate_parent flag to user profile and require for enrollment.

5. FRL Cycle Alignment (Ambiguous)

Issue: Spec states FRL "resets annually" but doesn't clarify whether it aligns with calendar year or employment anniversary.

Recommendation: Clarify in policy: FRL follows calendar year (Jan 1 reset) or employment anniversary.

Effort: 4–5 hours (endpoint + UI + tests)

Effort: 6–8 hours (scheduler + template + testing)

🎯 Implementation Quality Assessment

Strengths

  • BCEA Compliance: Accrual calculations are correct and thorough. Proper handling of graduated accrual, cycle resets, and statutory entitlements.
  • Audit & Compliance: Comprehensive audit trail logs all significant actions. Supports compliance verification and dispute resolution.
  • Workflow Design: Multi-stage approval workflow with discretion logging is well-implemented. Allows HR to track decision rationale.
  • Extensibility: Custom leave type system with phased accrual rules allows flexibility without code changes.
  • Data Integrity: Robust validation prevents common errors (overlaps, insufficient balance, pre-start bookings, >12-month advance bookings).
  • Modular Architecture: Clear separation of concerns: routes.ts (API), bcea.ts (calculations), leave-accrual.ts (processing), email.ts (notifications).
  • Half-Day Support: Advanced feature for flexible leave taking is fully implemented.

Areas for Improvement

  • Configuration as Code: Some policy values (7-day notice, cycle start, FRL reset timing) are hardcoded or implicitly embedded. Moving them to configurable settings would improve flexibility.
  • Enforcement Clarity: Medical certificate requirements are flagged but enforcement is implicit. Should be explicit in HR approval validation.
  • User Experience: Employees cannot self-update contact info, requiring HR involvement for routine changes.
  • Manager Analytics: No team-level leave analytics or proactive alerts. Managers must manually check calendars.
  • Documentation: Some spec ambiguities (FRL cycle timing, Commissioning leave eligibility) need clarification in policy docs.
